# 자연어 검색 고도화 검토

라이브러리 자연어 검색(하이브리드 검색) 코드를 읽고 정리한 검토 결과. 구현 전 아이디어 단계이며, 아래 어떤 항목도 아직 코드에 반영되지 않았다.

## 현재 구조 요약

- `javstory/services/library_service.py:481` `search_items()` — `_looks_like_natural_language()`로 자동 판별 후 `HybridLibrarySearch.search_embedding_union_bm25()` 호출
- `javstory/search/library_search.py` — BM25(rank_bm25) ∪ 임베딩(ANN, numpy matmul) 결과를 합침. RRF 융합(`search_with_fusion`)도 구현돼 있지만 **실제 UI 경로에서는 안 씀**
- `javstory/library/embeddings/query_format.py` — e5-instruct 쿼리 템플릿 + 수작업 동의어 사전(분위기/장소/장르 ~90개 그룹) + DB 장르 자동 인덱싱
- `javstory/library/embeddings/document_builder.py` — meta/grok_story/subtitles/scene 단위로 문서 분리해 임베딩
- `javstory/persona/library_search.py` — 페르소나 챗 전용의 훨씬 정교한 규칙 기반 쿼리 파서(품번 추출, 제목-정확매칭, source_policy 분기, grok 캐시 전문검색)가 **별도로 존재**하며 메인 라이브러리 검색창과 공유되지 않음

## 발견한 문제 / 고도화 포인트 (우선순위순)

### 1. 자막(SRT) 임베딩이 앞부분만 반영됨 — 실질적 기능 결손

`document_builder.py:217-232`에서 자막 전체(최대 20만자)를 **단일 문서**로 만들고, `pipeline.py:151-166` → `truncate_embedding_input()`(`llamacpp_embeddings.py:468`)이 모델 컨텍스트(ctx-128자, 보통 수천자)로 **앞부분만 잘라** 임베딩한다. 2시간 분량 대사의 대부분이 검색 대상에서 제외되는 셈이다. scene 문서가 이를 일부 보완하지만 canonical.scenes가 없는 작품은 완전히 빠진다.

→ 자막을 시간/글자 단위로 청킹해 여러 문서로 나누면 "특정 대사/장면" 검색 정확도가 크게 개선될 여지가 있다.

### 2. RRF 융합 경로(`search_with_fusion`, metadata 채널)가 사실상 죽은 코드

`_search_metadata`(배우/장르/제작사 토큰 매칭)와 `JAVSTORY_HYBRID_SEARCH_WEIGHTS` env는 `search_with_fusion`에서만 쓰이는데, 실제 서비스는 `search_embedding_union_bm25`만 호출한다(`library_service.py:544`). 즉 설정 문서/env에 노출된 가중치 튜닝이 실질적으로 검색 결과에 영향을 못 준다. 정리하거나(사용하지 않는 코드 제거) 혹은 실제로 채널을 다시 살릴지 결정 필요.

### 3. 부정/제외 표현 미지원

"~빼고", "~말고", "~아닌" 같은 제외 조건을 파싱하는 로직이 없다. BM25/임베딩 모두 이런 토큰을 그냥 긍정 신호로 흡수해버려 "유부녀 아닌"류 쿼리가 오히려 반대로 작동할 수 있다.

### 4. 구조화 필터 자동 추출 없음

"작년에 나온 여배우 A 작품 중 비오는 장면" 같은 복합 쿼리를 배우/기간/분위기로 분해해 DB 필터(genres, release_date 등)와 시맨틱 쿼리로 나누는 로직이 없다. `persona/library_search.py`에는 품번/제목 추출 로직이 이미 있지만 메인 검색과 연결되지 않았다 — 이 자산을 재사용해 "쿼리 사전처리 단계"를 추가하면 얻는 게 크다.

### 5. 동의어 사전이 정적/수작업

`query_format.py`의 `_SETTING_CONCEPTS`/`_GENRE_CONCEPTS`는 하드코딩된 딕셔너리다. DB 장르는 자동 인덱싱되지만(`_load_live_genre_concepts`), 배우 별칭/이형 표기, 신조어 은어 등은 사람이 계속 추가해야 확장된다. 이미 로컬 LLM(llama-server)이 떠 있으므로, 미등록 토큰이 자주 매칭 실패할 때 LLM에게 동의어 후보를 물어 사전에 반영하는 오프라인 배치를 고려할 만하다.

### 6. 재랭킹(rerank) 부재

1등 근접 유사도만 남기는 통계적 컷오프(`_filter_relevant_embedding_hits`)는 잘 만들어져 있지만, 상위 N개를 LLM/cross-encoder로 재정렬하는 단계는 없다. 복합·미묘한 쿼리("피곤한 유부녀가 마지못해 응하는 느낌")에서 순수 코사인만으로는 뉘앙스 구분이 약할 수 있다. 이미 chat용 llama-server가 구동 중이므로, "정밀 모드" 같은 옵션으로 상위 20~30건만 LLM 재랭킹하는 방식은 지연시간 대비 구현 비용이 낮은 편이다.

### 7. 검색 결과에 "왜 매칭됐는지" 설명 없음

`similarity.py`의 `find_similar_products`(유사작품 추천)에는 `match_reasons`(스토리 구성/배경 매칭)를 만드는 로직이 있는데, 메인 라이브러리 검색에는 이런 설명이 없다. 매칭된 concept/scene 태그를 하이라이트해주면 사용자가 쿼리를 다듬기 쉬워진다.

### 8. 쿼리 캐시가 완전 일치만 히트

`_embed_search_cache_key`(`library_search.py:253`)는 원문 그대로를 해시하므로 "비 오는 날" vs "비오는날"이 캐시 미스가 된다. 조사 제거·공백 정규화 후 키를 만들면 캐시 적중률을 높일 수 있다(임베딩 재계산 비용 절감).

### 9. ANN 인덱스가 진짜 ANN이 아님 (brute-force matmul)

`ann_index.py`는 이름과 달리 전체 벡터 내적을 numpy로 계산한다. 현재 라이브러리 규모에서는 충분히 빠르지만, scene 단위 문서까지 포함해 문서 수가 수만~수십만으로 늘어나면 매 쿼리마다 풀스캔 비용이 체감될 수 있다. 지금 당장 문제는 아니지만 확장성 메모로 남겨둘 만하다.

## 정리

가장 임팩트 대비 비용이 낮은 순으로 추천한다면:

1. **자막 청킹** (검색 가능한 콘텐츠 자체가 늘어남)
2. **부정어 처리**
3. **persona의 쿼리 파서를 메인 검색에 연결** (구조화 필터 + 제목 정확매칭 재사용)
4. **선택적 LLM 재랭킹**

2번 항목(RRF/metadata 죽은 코드)은 기능 추가라기보다 정합성 정리(사용하지 않는 설정 제거) 항목이다.
